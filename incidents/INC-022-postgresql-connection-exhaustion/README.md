# INC-022 — PostgreSQL Connection Exhaustion

## Summary

A controlled PostgreSQL connection-exhaustion incident was reproduced in the NIGHTWATCH lab.

The database remained running, but nearly all available client connection slots were consumed by intentionally opened sessions. Once the connection limit was reached, additional clients were rejected with:

```text
FATAL: sorry, too many clients already
```

After the artificial load was released, connection usage returned to normal and both database connectivity and application traffic recovered.

## Baseline

Initial PostgreSQL configuration and usage:

```text
max_connections = 100
current_connections = 7
```

The database had significant unused connection capacity before the incident.

## Failure Injection

Controlled PostgreSQL sessions were opened using application-specific connection tags such as:

```text
opsforge-inc022-load2
opsforge-inc022-exhaust
opsforge-inc022-lastmile
```

These tags were used only to distinguish the lab-generated sessions from normal application sessions during the test.

During saturation, client backend usage approached the configured connection limit.

## Observed Failure

A final connection probe produced:

```text
CONNECTED 1
CONNECTED 2
CONNECTED 3
REJECTED OperationalError:
connection failed: connection to server at "172.22.0.3", port 5432 failed:
FATAL: sorry, too many clients already
```

This confirmed that PostgreSQL itself was still running but had exhausted available client connection slots.

## Investigation

### 1. Verified PostgreSQL configuration

```text
max_connections = 100
superuser_reserved_connections = 3
```

### 2. Verified client backend usage

`pg_stat_activity` was used to distinguish client connections from PostgreSQL background processes. At peak pressure, approximately all usable client connection capacity had been consumed.

### 3. Identified tagged load sessions

The majority of sessions were attributable to the controlled incident traffic. This ruled out uncontrolled application traffic and confirmed that the pressure was generated by the lab test.

### 4. Distinguished capacity exhaustion from other failures

The error was not caused by authentication failure, a PostgreSQL crash, DNS failure, or general network connectivity loss. The decisive evidence was:

```text
FATAL: sorry, too many clients already
```

## Root Cause

PostgreSQL reached its configured maximum number of concurrent client connections.

The database remained running, but new client sessions could not be accepted because all available connection slots were already in use.

## Resolution

The controlled load-generator processes exited, releasing their PostgreSQL sessions.

Post-recovery client backend usage returned to:

```text
client_backends = 2
```

A fresh database connection succeeded:

```text
RECOVERY_CONNECTION_OK
```

Application readiness also returned healthy, and a valid database-backed ticket request returned:

```text
HTTP/1.1 200 OK
```

## Preventive Actions

- Monitor PostgreSQL connection utilization as a percentage of `max_connections`.
- Alert before connection usage reaches critical levels.
- Use connection pooling where appropriate.
- Configure sensible application pool limits.
- Investigate long-lived idle connections.
- Track connections by `application_name`.
- Monitor connection acquisition errors.
- Set application-side connection and pool timeouts.
- Consider PgBouncer or another pooling layer for high-concurrency workloads.
- Document emergency procedures for identifying and terminating runaway sessions.
