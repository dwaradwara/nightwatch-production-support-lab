# OPSFORGE Baseline Telemetry Contract

This document defines the normal-state signals OPSFORGE uses before incident simulation begins.

It deliberately does **not** invent a latency or capacity baseline from one CI run. CI proves that required signals exist and that the stack can become operational; controlled repeated load tests will establish defensible performance baselines later.

## Health contract

A running container is not automatically a healthy service.

### API process health

`GET /health/live`

Meaning: the Flask process is alive and capable of returning HTTP.

This endpoint does not claim that application dependencies are healthy.

### API readiness

`GET /health/ready`

Ready requires:

- PostgreSQL reachable and able to execute `SELECT 1`
- Redis reachable and able to respond to `PING`

If either dependency fails, readiness returns HTTP `503`.

### Worker readiness

Prometheus metric:

```text
nightwatch_worker_ready
```

Expected normal value:

```text
1
```

The worker becomes ready only after:

- RabbitMQ connection established
- queue declared
- consumer registered

Container process state by itself is not enough.

### RabbitMQ consumer state

The queue `nightwatch-jobs` must have at least one active consumer during normal operation.

This distinguishes:

- RabbitMQ available but no worker consuming
- worker process alive but not registered
- healthy asynchronous processing path

## API telemetry

### Dependency availability

```promql
nightwatch_dependency_up
```

Normal expectation:

- `dependency="postgresql"` = `1`
- `dependency="redis"` = `1`

### Dependency health-check outcomes

```promql
nightwatch_dependency_checks_total
```

Use this to identify dependency-check failures and recurrence patterns.

### Dependency latency

Metric:

```text
nightwatch_dependency_latency_seconds
```

Example PostgreSQL/Redis p95 query:

```promql
histogram_quantile(
  0.95,
  sum by (le, dependency) (
    rate(nightwatch_dependency_latency_seconds_bucket[5m])
  )
)
```

Purpose: distinguish application response degradation from dependency degradation.

### Application database query duration

Metric:

```text
nightwatch_db_query_duration_seconds
```

Example p95 query:

```promql
histogram_quantile(
  0.95,
  sum by (le, operation) (
    rate(nightwatch_db_query_duration_seconds_bucket[5m])
  )
)
```

The current `tickets_list` operation is instrumented. Additional business operations will be instrumented as Phase 2 adds customer workflows.

### HTTP request signals

The API also exposes the standard Flask/Prometheus request metrics generated by `prometheus-flask-exporter`.

OPSFORGE will use those signals for:

- request volume
- HTTP status distribution
- error-rate analysis
- endpoint latency analysis

Exact performance thresholds will be established after repeatable load testing rather than inferred from CI startup traffic.

## Worker telemetry

### RabbitMQ connection

```promql
nightwatch_worker_rabbitmq_connection_up
```

Normal expectation: `1`.

### Worker readiness

```promql
nightwatch_worker_ready
```

Normal expectation: `1`.

### Job processing rate

```promql
sum by (result) (
  rate(nightwatch_worker_jobs_processed_total[5m])
)
```

This will allow OPSFORGE to distinguish successful processing from repeated failures after Phase 2 begins publishing real workflow jobs.

### Job duration

Metric:

```text
nightwatch_worker_job_duration_seconds
```

This will be used to identify background-processing degradation and backlog-related incidents.

## RabbitMQ telemetry

RabbitMQ exposes Prometheus metrics through the `rabbitmq_prometheus` plugin.

CI currently verifies that RabbitMQ telemetry reaches Prometheus using:

```text
rabbitmq_identity_info
```

Later incident dashboards will add queue-specific signals such as queue depth, consumer count, publish rate, acknowledgement rate, and unacknowledged messages.

## Cross-signal request correlation

Nginx owns the canonical edge request ID.

For a customer-facing request, the troubleshooting path is:

```text
HTTP response X-Request-ID
        |
        v
Nginx structured access log
        |
        v
API structured request log
        |
        v
Tempo span attribute
nightwatch.request_id
```

Tempo TraceQL lookup:

```traceql
{ span."nightwatch.request_id" = "<request-id>" }
```

CI proves the same edge-generated request ID can be found in:

- the HTTP response
- Nginx logs
- API logs
- Tempo traces

This is the minimum correlation path for later L2 incident exercises.

## Grafana data sources

Grafana is provisioned from repository configuration with:

- Prometheus
- Loki
- Tempo

CI verifies all three data sources exist through the Grafana API.

The repository therefore does not rely on manually recreating observability configuration after startup.

## Initial service objectives

The OPSFORGE operating model currently defines training objectives of:

- availability >= 99.9% during scheduled simulation windows
- API p95 latency < 500 ms under baseline load
- HTTP 5xx rate < 1% under baseline load
- synthetic critical journey success >= 99% during scheduled simulation windows

These are **service objectives**, not measured current performance claims.

## Performance-baseline rule

OPSFORGE will not publish numbers such as "normal p95 is 80 ms" based on one laptop run or one GitHub Actions runner.

A defensible performance baseline requires:

1. a defined customer transaction
2. fixed dataset/state
3. controlled request rate
4. repeated test windows
5. known application version
6. known environment configuration
7. captured p50/p95/p99, throughput, error rate, dependency latency, queue state, and resource behavior

That work belongs after the Phase 2 customer journey exists.

## Phase 1 normal-state checklist

A baseline is considered operational when all of the following are true:

- API liveness returns HTTP 200
- API readiness returns HTTP 200
- PostgreSQL dependency signal is healthy
- Redis dependency signal is healthy
- worker readiness equals 1
- RabbitMQ has an active consumer on `nightwatch-jobs`
- Prometheus can query API, worker, and RabbitMQ telemetry
- Grafana has Prometheus, Loki, and Tempo provisioned
- public `/api/tickets` path succeeds through Nginx
- one edge request ID can be followed through Nginx log, API log, and Tempo trace

Failure of any required item means the environment has not reached the OPSFORGE production baseline.
